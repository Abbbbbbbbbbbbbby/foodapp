Food Line Check-In App — Final Design Spec

Complete and up to date. All changes applied. Reply in the terminal to approve or request changes.

Context

Replacing the Creighton Community Foundation's Bubble.io food distribution check-in app with a mobile-first PWA on Cloudflare. Same data model and logic — faster, more accessible, and resilient to spotty outdoor network conditions. Designed for older volunteers, bilingual interactions, and community families who may not speak English.

Three Roles

Volunteer
Community volunteers. Can only enter data. Home screen shows one button. Self-registers with name + phone. Role defaults to volunteer.
Staff
Org employees. Enter data + view all records + data summary. Cannot manage accounts. Home shows two buttons.
Admin
1–2 people. Full app access. Manages accounts, sets roles, controls page access for other roles, exports data.

Architecture — Cloudflare Pages + Workers + D1

Browser (PWA)
  ├─ Service Worker (offline queue + app shell cache)
  └─ IndexedDB (submission queue when offline)
           │ syncs when back online
           ▼
Cloudflare Workers (API) → D1/SQLite · KV (sessions) · Twilio (SMS OTP)
Cloudflare Pages (CDN — global edge delivery)
  • Works offline — submissions queue locally, sync when signal returns, no data lost
  • D1 SQL model maps directly to Bubble.io export — migration is a SQL import
  • Scales to zero between events

Auth — SMS OTP

  1. Anyone can self-register: enter name + phone → receive 6-digit SMS code → account created as volunteer
  2. Admin promotes accounts to staff or admin as needed
  3. JWT issued on login, cached in localStorage, 12-hour TTL — app works offline once logged in
  4. No passwords, no email, no area code autofill

Core Check-In Flow (/enter)

Step 0 — Have we saved your data before?
Yes / Sí → Returning path
No → New family path
Shown in both languages at equal size. No "read aloud" labels.
Returning path (~15 seconds)
  1. Lookup: Phone (blank, no autofill) and/or name (fuzzy, tolerates misspelling)
  2. Results: Ranked matches — name, partial phone, family size, last visit. "Not found → Register new" at bottom
  3. Select families: Own family first, then all proxy families. None pre-checked. Volunteer taps each being picked up today. Running count shown. Confirm disabled until ≥1 selected.
  4. Log per family: "No change" (marks visit) or "Update info" (mini-edit). After last family → Done.
New family path — Registration
Before the wizard: Duplicate check

If name or phone entered matches an existing record, app shows confirmation: "We may already have this family on file. Is this them?" — Yes switches to returning flow; No continues registration.

Before the wizard: Who usually picks up?

"They pick up for themselves" (skip) or "Someone else picks up for them" (collect proxy name + phone → saved to proxies table).

11-step wizard
Every step: both languages at equal size, no labels. Large tap targets. Back/Skip always visible. Progress bar.

Offline Strategy

  • App shell cached — instant launch, no signal needed
  • Submissions queue in IndexedDB, sync when online
  • Lookup requires network; offline banner shown
  • Valid JWT = app works offline once logged in

Accessibility

  • Min touch target: 48×48px
  • Min font: 16px body, 20px+ questions
  • High contrast dark theme — readable in sunlight
  • No time-outs on data entry
  • "Prefer not to say" never blocks submission

Data Migration

Source: food-data.bubble (682KB) + appdata20260213.csv in ~/Downloads. One-time Node.js script → SQL INSERTs for D1.

  1. Bubble family_data → families table (recalculate income → ami_bracket; discard raw income)
  2. visit_dates_list_date → one row per date in visits
  3. Proxy fields → proxies table
  4. Bubble users → users table
  5. Cross-check names/phones against CSV
