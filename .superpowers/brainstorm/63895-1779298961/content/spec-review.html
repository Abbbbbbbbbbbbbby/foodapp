Design Spec — Food Line Check-In App

Review the full spec below. Reply in the terminal with any changes you'd like before we start the implementation plan.

Context

Replacing the Creighton Community Foundation's Bubble.io food distribution check-in app with a mobile-first PWA on Cloudflare. Same data, same logic — dramatically better UX for older volunteers, bilingual interactions, and spotty outdoor network conditions.

Architecture

Browser (PWA)
  ├─ Service Worker (offline queue + app shell)
  └─ IndexedDB (pending submissions when offline)
        │ syncs when back online
        ▼
Cloudflare Workers (API)
  ├─ D1 / SQLite (all family + visit data)
  ├─ KV (session tokens)
  └─ Twilio (SMS OTP login)
Cloudflare Pages (CDN — serves PWA globally)
  • Works offline — submissions queue locally, sync when signal returns
  • No data lost if volunteer loses signal mid-event
  • D1 SQL model maps directly to Bubble.io export — migration is a SQL import
  • Scales to zero between events (Workers + D1 bill per request)

Authentication: SMS OTP

  1. Volunteer enters their phone number (no autofill)
  2. Twilio sends a 6-digit code by text
  3. Volunteer enters code → JWT issued, valid 12 hours
  4. JWT cached in localStorage → app works offline once logged in
  5. Admins create volunteer accounts in advance — volunteers cannot self-register

App Pages

/loginAll users — phone number + OTP
/Home — two big buttons: Enter Data / View Data
/enterCore check-in flow (volunteers)
/enter/proxy-formsAdd proxy authorization for a family
/viewSearch family records (volunteers + admins)
/admin/accountsManage volunteer accounts (admin only)
/admin/exportCSV data export (admin only)
/accountAccount settings (all users)

Core Check-In Flow (/enter)

Step 0 — New or Returning?

Two large buttons. Read aloud: "Are you returning, or is this your first time?" / "¿Está regresando, o es su primera vez?"

RETURNING PATH (~15 seconds)
  1. Lookup: Phone (blank, no autofill) and/or name (fuzzy search, tolerates misspelling)
  2. Results: Ranked matches — name, partial phone, family size, last visit date. "Not found → Register as new" at bottom
  3. Select families: Own family shown first, then all proxy families. None pre-checked — volunteer taps each family being picked up today. Running count shown. Confirm disabled until ≥1 selected
  4. Log visit per family: Name + size + last visit shown. "No change" (marks visit) or "Update info" (mini-edit). After last family → Done
NEW FAMILY PATH — 11-step wizard (~2 min)

Every step shows: English sentence (green, read aloud) + Spanish sentence (purple, read aloud). Large tap targets. Back/Skip always visible.

1 "What is your full name?" Text input
2 "What is your phone number?" Phone + "No phone / Sin teléfono"
3 "What is your zip code?" Numeric input
4 "What language do you prefer?" English / Español / Other
5 "How many people live in your household?" Tap: 1 / 2 / 3 / 4 / 5 / 6+
6 "How many children under 18?" Tap: 0–6+
7 "How many children under 5?" Tap: 0–5+
8 "What is your approximate monthly household income?" Tap: <$500 / $500–$1k / $1k–$2k / $2k+ / Can't answer
9 "Does your family currently receive SNAP benefits?" Yes / No / Can't answer
10 "Does anyone in your family have health insurance?" Yes / No / Can't answer
11 "May we send you text message updates?" Yes / No

Fuzzy Name Search

  • Phone: exact match on normalized digits
  • Name: Levenshtein distance ≤2 on first token, ≤3 on full name — tolerates common misspellings
  • Combined: union of results, ranked (exact phone first, then name distance)
  • Proxy expansion: also returns all families where the person's phone is listed as an authorized proxy

Offline Strategy

  • App shell cached on first load — launches instantly with no signal
  • Family lookup requires network — offline banner shown if unavailable
  • Submissions (new families + visits) queue in IndexedDB, sync when signal returns
  • Valid JWT in localStorage = app keeps working offline once logged in
  • Duplicate dedup on sync: phone as soft key, later record wins, flagged for admin review

Bilingual Design Rules

  • Every question = full readable sentence in English (green) and Spanish (purple) — same size, volunteer reads one aloud to client
  • All button labels bilingual: "Yes / Sí", "Search / Buscar", "Confirm / Confirmar"
  • Language preference saved per family, pre-shown on returning visits
  • Admin screens (export, accounts) are English-only

Accessibility & Usability

  • Minimum touch target: 48×48px on all interactive elements
  • Minimum font: 16px body, 20px+ for question text
  • High contrast dark theme — readable in sunlight
  • No time-outs on data entry screens
  • Destructive actions require a second tap to confirm
  • "Can't answer" on every sensitive field — never blocks submission

Data Migration

Source: food-data.bubble (682KB JSON) already in ~/Downloads.

  1. Bubble family_data → D1 families table
  2. visit_dates_list_date per family → one row per date in visits
  3. proxies_list_text + phone numbers → proxies table
  4. Bubble user type → D1 users table
  5. appdata20260213.csv as cross-check on names + phones

One-time Node.js migration script reads Bubble JSON → emits SQL INSERTs for D1.
